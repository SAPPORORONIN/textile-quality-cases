# 质量数据与指标架构

> **Quality Data & Metrics Architecture for Textile & Apparel**

---

## 一、 为什么需要质量数据架构

质量数据散落在多个系统中——检验报告在 Excel 里，测试结果在实验室系统里，退货数据在电商后台，供应商评分在另一个 Excel 里。没有统一的数据架构，就无法：
- 知道"今年质量到底好了还是差了"
- 回答"哪个供应商的哪类产品问题最多"
- 论证"质量投入的回报是多少"

本框架定义质量数据的**层级、指标体系、数据流向和治理规则**。

---

## 二、 质量数据层级模型

```
┌─────────────────────────────────────────────────┐
│            Level 4: 战略指标                      │
│     COQ 占收入比、质量成熟度等级、NPS             │
│     受众: C-Suite / Board                        │
├─────────────────────────────────────────────────┤
│            Level 3: 管理指标                      │
│     FTR 趋势、8D 关闭率、索赔回收率              │
│     受众: QA 总监 / VP                           │
├─────────────────────────────────────────────────┤
│            Level 2: 运营指标                      │
│     AQL 通过率、IQC 合格率、Cpk、供应商评分      │
│     受众: QA 经理 / 工程师                       │
├─────────────────────────────────────────────────┤
│            Level 1: 原始数据                      │
│     检验记录、测试报告、退货明细、8D 档案         │
│     受众: QC / 检验员 / 实验室                   │
└─────────────────────────────────────────────────┘
```

每一层的指标由下一层的数据汇总而来，不是独立定义的。

## 三、 核心指标体系

### 3.1 结果指标（Outcome Metrics）

衡量质量管理的**最终效果**。

| 指标 | 定义 | 计算方式 | 目标方向 | 频率 | 案例参考 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **FTR（First Time Right）** | 终检一次合格率 | 终检合格批次 / 终检总批次 | ↑ Higher | 月度 | [SYS-001](case:SYS-001) |
| **质量原因退货率** | 经实物复核归因于产品质量缺陷的退货比例 | 质量退货件数 / 售出件数 | ↓ Lower | 月度 | [HT-012](case:HT-012) |
| **8D 关闭周期** | 从立案到关闭的天数 | 中位数（按严重度分层） | ↓ Lower | 月度 | [SYS-011](case:SYS-011) |
| **重复问题率** | 同供应商同失效模式 12 月内再发比例 | 重复 8D 数 / 8D 总数 | ↓ Lower | 季度 | [SYS-011](case:SYS-011) |
| **索赔回收率** | 实际回收金额占应索赔金额的比例 | 回收金额 / 应索赔金额 | ↑ Higher | 季度 | [SYS-011](case:SYS-011) |
| **COQ 占收入比** | 质量总成本占营收比例 | COQ / Revenue | ↓ Lower | 年度 | [FW-COQ](doc:FW-COQ) |

### 3.2 过程指标（Process Metrics）

衡量质量管理**过程的健康度**。

| 指标 | 定义 | 目标方向 | 频率 | 案例参考 |
| :--- | :--- | :--- | :--- | :--- |
| **IQC 来料合格率** | 来料检验批次合格率 | ↑ Higher | 月度 | [SOP-IQC](doc:SOP-IQC) |
| **AQL 检验覆盖率** | 实际执行 AQL 检验的批次 / 应检批次 | ≈ 100% | 月度 | [SYS-009](case:SYS-009) |
| **Cpk（关键指标）** | 过程能力指数 | ≥ 1.33 | 逐批 | [PB-SPC](doc:PB-SPC) |
| **供应商审厂完成率** | 按计划完成审厂 / 应审数 | ≈ 100% | 季度 | [SYS-010](case:SYS-010) |
| **实验室比对 kappa** | 实验室间评定一致性系数 | ≥ 0.80 | 年度 | [PB-MSA](doc:PB-MSA) |
| **追溯定位时间** | 从产品到批次的追溯耗时 | ≤ 24h | 年度演练 | [SYS-012](case:SYS-012) |

### 3.3 先导指标（Leading Indicators）

预测未来质量趋势的**早期信号**。

| 指标 | 定义 | 信号含义 |
| :--- | :--- | :--- |
| 新供应商占比 | 新供应商订单 / 总订单 | 比例过高 → 质量风险升高 |
| 产前会完成率 | 按时召开产前会的款 / 应召开款 | 偏低 → 预防不足 |
| FMEA 覆盖率 | 有 FMEA 的品类 / 全部品类 | 偏低 → 盲区 |
| 测试超期率 | 测试报告超过交期的批次 | 偏高 → 流程瓶颈 |
| SPC 失控点处置率 | 已调查的失控点 / 总失控点 | 偏低 → 控制图形同虚设 |

## 四、 数据流向与系统映射

### 4.1 数据源

| 数据源 | 产生的数据 | 格式 |
| :--- | :--- | :--- |
| 检验系统（DQA / IQC） | 检验记录、AQL 结果、四分制评分 | 结构化数据 |
| 第三方实验室 | 测试报告（物理、化学、安全） | PDF + 结构化摘要 |
| 质量管理系统 | 8D 记录、NCR、CAPA | 结构化数据 |
| ERP / PLM | PO、SKU、供应商主数据、BOM | 结构化数据 |
| WMS | 入库批次、库存、发货记录 | 结构化数据 |
| 电商后台 | 退货原因、消费者评论 | 半结构化 |
| 审厂系统 | 审厂报告、评分 | 结构化 + 文档 |

### 4.2 数据汇聚

```
检验系统 ──┐
实验室    ──┤
8D 系统   ──┼──> 质量数据湖/仓库 ──> 指标计算引擎 ──> 仪表盘 / 报告
ERP       ──┤
WMS       ──┤
电商后台  ──┘
```

**现实路径**：大多数纺织服装企业不需要数据湖——从 Excel + BI 工具（Power BI / Tableau）开始，覆盖核心指标即可。关键是**定义清晰 + 数据源唯一 + 更新可靠**，而不是工具多先进。

### 4.3 指标口径唯一来源

本案例库的 `registry/metrics.json` 就是指标口径的唯一事实来源（Single Source of Truth）。每个指标有：
- **定义**：精确的计算公式和统计口径
- **单位**
- **方向**（higher / lower）
- **是否允许计算 Cpk**

企业在构建自己的质量数据架构时，应建立类似的指标注册表，避免"FTR 到底是按 SKU 算还是按 PO 算"的争论。参考 [SYS-001](case:SYS-001) 中 DQA 标准化体系对 FTR 口径的统一实践。

## 五、 数据治理规则

### 5.1 数据质量要求

| 规则 | 说明 |
| :--- | :--- |
| **完整性** | 每批检验记录必须在 24 小时内录入系统 |
| **准确性** | 数字与测试报告原件一致，不允许手动修改已录入的检验数据（修正需审批记录） |
| **一致性** | 同一指标在所有报告和系统中用同一口径 |
| **时效性** | 月度指标在次月 5 个工作日内发布 |
| **可追溯** | 任何一个汇总数字都能追溯到原始检验记录 |

### 5.2 数据权限

| 数据层级 | 可查看 | 可修改 |
| :--- | :--- | :--- |
| Level 1 原始数据 | QC + QA 工程师 + QA 经理 | QC（录入），QA 工程师（审核） |
| Level 2 运营指标 | QA 团队全体 | 系统自动计算，不允许手动覆盖 |
| Level 3 管理指标 | QA 管理层 + 采购 | 系统自动计算 |
| Level 4 战略指标 | 高管层 | QA 总监（汇编） |

## 六、 报告节奏

| 报告 | 频率 | 核心内容 | 受众 |
| :--- | :--- | :--- | :--- |
| **质量日报** | 每日 | 当日检验结果摘要、异常预警 | QA 工程师 |
| **质量周报** | 每周 | 本周 FTR、8D 状态、重点问题 | QA 经理 |
| **质量月报** | 每月 | 全指标仪表盘 + Top 5 问题 Pareto + 供应商排名 | QA 总监 |
| **供应商季度评审** | 每季 | 记分卡 + 等级变更 + 改善计划 | QA 总监 + 采购 VP |
| **质量年度报告** | 每年 | COQ + 成熟度自评 + 年度改善总结 + 次年目标 | C-Suite |

## 七、 与案例库的关系

本案例库本身就是质量数据架构的一个实践：
- `registry/metrics.json` = 指标注册表
- `case.json` 中的 `metrics` 字段 = 原始数据到结果的映射
- `case.json` 中的 `ledger` 字段 = COQ 数据的源头
- `scripts/validate.js` = 数据治理规则的可执行实现
- `governance/` = 数据治理规则的文档化
